## Writer note: round 1

- Finding 1 (P1, `--write` could delete the instructions and the block after an unclosed block) is real: `units` searched forward for any later closing fence, so a block missing its own fence took in everything up to the next one, was read as well formed and stale, and was replaced whole. Fixed at its cause in the commit after this round's candidate: a block is rows and nothing else, so `units` reads it line by line and ends it at the first line that is its closing fence; a blank line, another `**Layout:**` line or another fence before that makes the block one that was never closed (a refusal, never a rewrite), and nothing up to the interrupting line is read as the start of another unit. A unit therefore never holds a line the generator did not write, which is the property `rewrite` rests on. The same question asked of the rest: `rewrite` replaces only well-formed units of open sections and finds each section by its own heading, and a failed write leaves the file as it was.
- Tests: `test_an_unclosed_block_never_takes_in_what_follows_it` builds the reviewer's case in a file (a stale block with its fence left out, instructions with a code fence of their own, then a second block), requires the second block to be read whole and alone, `--write` to leave every byte unchanged and exit 1 naming the unclosed block, and, with the fence put back, the stale block rewritten with the instructions and the second block untouched. The malformed-block test now also holds a section that ends inside a block, a blank line inside one and another fence inside one.
