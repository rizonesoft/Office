# Campaign scope and unattended-run decisions

Recorded 2026-10-23 from the owner's answers of 2026-10-22, given in one session before the first unattended `process-plan` campaign so the run never has to stop and ask. Every TODO section these decisions touch cites this record. A later change of mind is a new dated decision here, never an edit of an old one.

## Context

The suite moved on 2026-10-22 from WinUI 3 in C# on .NET 11 to native C++ (C++23 on MSVC `/std:c++23preview`, moving to C++26 once MSVC ships a stable flag for it) with our own GUI toolkit on Win32, Direct2D and DirectWrite, Windows only (D03 T01 §1, §2). The owner wants to start one campaign and come back to a finished, production-ready suite after days, weeks or months. At the time of the record the plan held 95 sections, 36 stamped, and stopped at Phase 3: the platform, the six apps, interoperability and release (Phases 4 to 7) had no sections, and 22 open sections waited on an owner, an operator, Office captures or a display session.

The owner also asked that Outlook (classic), Visio and Project, whose interfaces look dated beside Word, Excel and PowerPoint, be brought up to the same standard.

## Decision

Owner, 2026-10-22, in session:

1. **Run host:** this PC, signed in and unlocked, with sleep and screen lock off. Microsoft 365 Apps (Word, Excel, PowerPoint, Outlook classic), Visio and Project stay installed for the Phase 2 captures, and nobody uses the PC while a capture section runs.
2. **Keep-alive:** none. The owner resumes a stopped campaign by hand, which keeps the freedom to stop and start it at will. The run guard, Stop hook and in-session heartbeat stay as they are.
3. **Sign-offs:** the pinned independent reviewer signs off the icon review (D01 T02 §7) and the mockups (D02 T02 §14) against their briefs; each sign-off is recorded with its evidence, and the owner audits it later and may reopen it.
4. **Outward actions:** the campaign pushes to `main`, merges green dependency pull requests under the existing rule, and creates draft GitHub releases. It never publishes a release.
5. **Modernisation:** Outlook, Visio and Project keep every inventoried command in its tab and group, and take the Word, Excel and PowerPoint design: title bar with search, Fluent glyphs, rounded controls, Mica, dark mode, the Simplified Ribbon option, Backstage, panes, dialogs and status bar. A layout changes only where Word, Excel or PowerPoint has a newer pattern for the same job, and each change is recorded in `design/SPEC.md`.
6. **Microsoft cloud features:** each gets a working equivalent of our own: an Assistant pane on a provider the user configures (Anthropic, OpenAI or a local model, off by default), Windows speech for dictation, open image libraries, a local grammar engine. A feature with no possible equivalent is marked excluded in the inventory with its reason, never left as a dead control.
7. **Cloud scope for 1.0:** OneDrive and SharePoint open and save with AutoSave through Microsoft Graph; Mail on Microsoft 365 and Outlook.com (Graph), Gmail (Google OAuth), iCloud and any IMAP and SMTP server, with CalDAV and CardDAV. Real-time co-authoring comes after 1.0. The owner registers a Microsoft Entra application and a Google OAuth client; until then only the sections that need them wait.
8. **Macros:** VBA projects always survive save. A sandboxed VBA-compatible runtime and editor with Trust Center rules is the final milestone, after all six apps reach parity.
9. **Minimum OS:** Windows 11 24H2 and later, x64 and Arm64. Reaffirmed 2026-10-23 when asked whether Arm64 should go: native Arm64 from the start, built and tested in CI on every push, with red Arm64 runs repaired like any other (D00 T03 §15).
10. **UI languages:** English (United States) in 1.0, with every string externalised, right-to-left mirroring proven with a pseudo-locale, and translation files ready for contributors. Documents work in every language.
11. **Signing:** unsigned for now. Release sections that need a signature wait on an owner decision; everything else ships unsigned drafts.
12. **Updates and diagnostics:** the Inno Setup build checks GitHub Releases for updates; crash dumps stay on the user's PC, and the user may attach one to a pre-filled GitHub issue. No telemetry and no Rizonesoft service.
13. **Release cadence:** a draft preview release per app as its milestone passes (the first app first), and the suite's 1.0 draft when all six apps and the interoperability gates pass.
14. **Store:** no Microsoft Store. The MSIX package waits on signing (11); the Inno Setup installer is the channel.
15. **Toolchain:** the owner runs one elevated command before the campaign starts, adding the LLVM clang tools to Visual Studio 2026 18.11 (the C++ desktop workload, the Arm64 tools, CMake, vcpkg and the Windows SDK 10.0.26100 were already installed on 2026-10-23).

Owner, 2026-10-23, in session (asked so the unattended run never stops on versioning):

16. **Version scheme:** one Semantic Versioning 2.0 version for the whole suite, shared by all six apps: `0.x` for the per-app previews, `1.0.0` at the 1.0 gate, pre-release tags such as `1.2.0-preview.3`. Windows binaries carry four numbers, `MAJOR.MINOR.PATCH.BUILD`, with `BUILD` from CI; the update check compares SemVer precedence.
17. **Release notes and bumps:** generated from the TODO sections stamped since the last release tag, grouped by app, with the bump proposed from them (a new feature minor, a fix patch, a breaking file-format or object-model change major). The commit style stays as it is.
19. **Product bar:** we build a better product, not a clone (owner, 2026-10-23, in the owner's words in `docs/product-principles.md`). Parity is the floor; every app beats Office's own times on this PC for the D03 T01 §29 workloads and aims for half of them; every app domain plans signature improvements with tests that prove them; and both review prompts ask whether a section merely copies Office where better was in reach.
18. **Provenance:** every draft release carries an SPDX software bill of materials built from the vcpkg dependencies, a GitHub build attestation of where and from which commit each artifact was built, and SHA-256 checksums. None of it needs a signing certificate.

## Consequences

- The plan's acceptance bar names the modernised positions and recorded exclusions (`todo/plan.json`).
- D01 T02 §7 and D02 T02 §14 lose their `owner-decision` Need; D01 T03 §5 (an operator upload) moves to Phase 99; D01 T01 §9 records that there is no Store.
- D02 T02 §10, §11 and §12 specify the modernised Visio, Project and Outlook surfaces; D02 T01 §28 adds a disposition to inventory records, and D03 T01 §14 decides each cloud feature's equivalent or exclusion.
- D03 T01 §1, §7, §8 and §9 carry decisions 7 to 9, 11 and 14; §15 and §16 record decisions 10 and 12; §17 to §27 author the platform, engine, six app, interoperability, VBA and release domains to a written contract, and §13 proves every inventory record is owned.
- D00 T03 §12 adds a host readiness check the campaign runs before it starts and at each phase, so an unattended run parks with a reason instead of failing on a locked screen or a missing tool.
- D03 T01 §28 records decisions 16 to 18, including how persisted formats and settings carry and migrate their own schema versions; §17 and §27 build from it, so every per-app draft release is versioned, noted and attested the same way.
- Sections that need the Entra or Google registration carry the `operator` Need, and signing sections carry `owner-decision`; a campaign takes every other ready row and leaves those for the owner's return.

## Owner decisions, 2026-11-10

Given in session while the repository was being readied for the Claude Code campaign. They add to the decisions above and change decision 2 as stated.

20. **Autonomy:** the campaign acts as the owner would and better: it decides, improves its own plan, skills, agents, runners, tools and methods, heals its own failures, and plans without a ceiling against the best software anyone ships (the owner's words are in `docs/product-principles.md`, "Act as the owner would, and better"). It asks only for what the owner alone holds.
21. **Self-healing start (changes decision 2):** there is still no scheduled keep-alive task, but the launcher (`scripts/start-campaign.ps1`) starts a new session when the one it started ends while the run guard is still held, which is how a died session looks. The owner keeps the freedom to stop: a run ended by its own rules releases the guard and the launcher stops, and closing the window stops everything.
22. **Main only:** all work is committed straight to `main`; no feature branches or pull requests for our own work.
23. **Portable build tools:** build tools are repo scoped and portable, fetched at pinned versions and hashes into an ignored folder in the clone by the bootstrap of D00 T04 §1 to §4 (the lock, the resolver, CI and the launcher), with the build settings that use them in D03 T01 §12 and §17; only Visual Studio's MSVC toolset and the Windows SDK stay host prerequisites.
24. **No machine paths:** no tool writes a machine's folder layout into its code (`scripts/tests/test_no_hardcoded_paths.py`).
25. **Agents that err are removed:** a subagent whose reply the main loop proves wrong is deleted from the fleet, and the main loop does that work from then on; quality matters more than delegation (`AGENTS.md`, Subagents).
26. **The plan shows the whole road:** `todo/implementation-plan.md` lists every TODO file that is still to be authored with the section that authors it (D00 T03 §31), and every section that implements inventoried controls carries their layout (order, type, size, position, key tip) as a generated block and proves it against the built app (D02 T01 §29 and §30, D03 T01 §17).
27. **Fable orchestrates, workers write:** the launcher starts the latest Fable by alias (replacing the latest Opus decided earlier the same day), which routes each piece of work to the cheapest tier that holds its own quality bar: a script, Haiku for verified lookups, Sonnet, Opus at an effort it sets, then itself, escalating one tier on evidence. Workers write only from a work packet; the orchestrator reads every diff, runs every gate and commits, and the independent review is unchanged (`AGENTS.md`, Subagents). The aim is a lower cost than building with Opus alone at the quality of building with Fable alone.
28. **Measured before it is built out:** three sections are each built three ways (Fable alone, Opus alone, orchestrated) from one commit and compared on cost, gates and independent review findings before the routing is extended (the ledger, more workers, more scripts). The result is recorded in `docs/reviews/`. Decided by the owner the same day, ahead of the result, and therefore not waiting on it: the effort ceilings (Sonnet and Haiku at most high, Opus and Fable at most medium, low preferred on Opus and Fable) and the third worker `principal-implementer` (Fable in a fresh context, low by default, medium at most). The measurement runs from the commit before both and does not test them.
29. **Lessons and a track record:** what reviews taught is kept as small reviewed files in git with a derived SQLite index (no vector database and no embeddings until a lesson that exists is shown not to be found), written only by the main loop from confirmed findings and owner decisions and never by an agent, handed to each section run and each work packet as the few that match; a ledger of packet outcomes gives each tier a score per kind of work, which changes routing and never what is checked. It is built to still work on day 300: no file grows without bound, and each area has a ceiling on active lessons that forces them to be merged or turned into checks (D00 T05 §1 to §8).
30. **The data chooses the lead model:** which model leads and whether it works alone or orchestrates workers is decided by a written rule over a measurement (cost, gates and blind review findings of the same sections built each way), measured again every 300 stamped sections and whenever a lead alias resolves to a new model; nobody chooses it by opinion and the owner is not asked again (D00 T03 §36 and §37). This replaces the fixed choice of decision 27; the tiers and rules of decision 27 apply whenever the chosen way orchestrates.
31. **Restarts stay manual (decision 2 and 21 stand):** asked again on 2026-11-10 with months of unattended running in view, the owner kept it: no scheduled task restarts the campaign and Windows does not sign itself in. After a reboot, a crash or a closed window the run waits for the owner to start the shortcut. The launcher's own restart of a session that died while its window is open stays. The owner controls the run with two desktop shortcuts, start and stop: stop writes a request the campaign honours at its next section boundary and can also end the running session at once (`scripts/start-campaign.ps1 -Stop`).
32. **Never wait, one weekly digest:** the run works around everything only the owner can do and builds everything that does not need it; once a week one email reports progress and lists what is waiting on the owner with the exact steps, and there is no other interruption. Choosing this is the owner's standing permission for that one email (D00 T03 §35).
33. **Parallel streams when safe:** once work is independent enough (the apps, after the shared platform), the system may run several streams, each in its own clone, with one integrator landing them on `main` in order under the full gates. This reverses one tree, one writer (and decision 22's no branches) for that case only; it is designed and measured before it is built, and starts only after a two-stream trial lands cleanly (D00 T03 §38 and §39). Worktrees and branches are fine for this and for any other tooling job, on the owner's condition: each is cleaned up when its job ends or reused when the job recurs, never left behind.
34. **Self-contained credentials:** the credentials the repository needs (the SMTP2GO key for its emails and the one-year Claude Code token for the launcher) are imported from 1Password into `.secrets/office.env`, an untracked file in the clone closed to every other user account, by `python scripts/import-secrets.py`; the mailer and the launcher read them from there, so a run needs neither WSL nor the vault. The owner accepts that the values are stored on this PC's disk.
35. **Opus leads and writes; Fable is on call (replaces decision 27):** the three-way measurement of 2026-11-10 (three sections, each built by Opus alone, by Fable alone and by Fable routing packets to workers; `docs/reviews/operating-mode-2026-11-10.md`) found Opus alone at less than half the cost of Fable alone, packet routing the most expensive and not the cleanest, and Opus's first-pass findings growing with difficulty where Fable stayed nearly clean. The owner's shape: one long session on the latest Opus leads; it hands each section's build and each round of review fixes to an Opus writer agent in a fresh context (`section-writer`) and reads every change itself; Sonnet agents only read; Haiku is retired; Fable (`principal-implementer`) is on call, taking a section over after review round 8 with a `P1` or `P2` still open or as soon as a finding reported fixed comes back, to re-think the failing unit, and building the architecture decision records of Phase 3 from the start. The round cap stays 33. The effort ceilings and the rule that a worker's change is read in full before it is committed stand (`AGENTS.md`, Subagents).
36. **The rule judges the cost to an approved review (refines decision 30):** a way of working is measured from build through every fix round to a review with no `P1` or `P2`, because the review always runs and a first-pass finding is a cost, not a disqualification. The 2026-11-10 measurement was extended with those fix rounds; D00 T03 §36 and §37 build the rule this way.
37. **A scheduled review loop:** the reviewer system is upgraded to the one the Recto repository runs. The pin holds a schedule and the dispatcher picks each pass's effort and lenses: a plan review before the build, a completion review, a first round at medium effort across the lenses, then low-effort adversarial rotation rounds, one medium escalation round after a rotation round that finds a `P1`, and the loop ending at the first round with no `P1` or `P2`. The Fable takeover of decision 35 is counted in rotation rounds only (after rotation round 8), and the cap of 33 is a cap on rotation rounds; the first round, the escalation rounds and the plan and completion reviews count toward neither. The reviewer itself does not change (D00 T03 §40 to §45).
38. **Table rows up to 120 characters:** the limit on a Markdown table row is 120 characters, raised from 100; the 88-character limit on a section title stands.
39. **Straight on main, again (narrows decision 33's last sentence):** after branches and worktrees for tooling jobs were allowed earlier the same day, the owner returned to the rule of decision 22: no branches and no worktrees for our own work. A job that needs a second copy of the tree, a measurement or a parallel stream, uses a separate clone under the scratch folder with only its own `main`, replayed onto this repository's `main` and deleted or reused afterwards. The branches outside tools make (`pins/*`, Dependabot, CI proof branches) are unchanged.
40. **The main session writes (2026-11-11, refines decisions 30 and 35):** the owner follows the development in the main session, so the Opus writer agent of decision 35 (`section-writer`) is removed and the lead builds every section and every round of review fixes itself. Sonnet agents still only read and Haiku stays retired. The Fable takeover of decision 35 stays as it was (after rotation round 8 with a `P1` or `P2` still open, or as soon as a finding reported fixed comes back, and the architecture decision records of Phase 3), now as the only agent that writes; its value is a fresh context that re-thinks the failing unit from every round's findings. Working alone is therefore fixed by the owner and no longer a question for the measurement of decision 30, which keeps choosing the lead model between the arms that work alone (D00 T03 §36 and §37).
41. **The plan lists sections, never TODO files (2026-11-12, supersedes the first clause of decision 26):** the owner read the plan's `Still to author` file tables as part of Phase 99 and ruled that the plan file must not reference TODO files; it lists individual sections, in order. For the TODO files still to be authored, `todo/implementation-plan.md` shows the sections that author them, in plan order, each with the number of files it still has to write, under `Not in the plan yet: sections still to be written`; each written file's sections then join the phase tables (D00 T03 §58).
42. **A launcher for each runner, and Claude Code at medium effort (2026-11-12):** the owner asked for the desktop shortcut to be renamed `Office Claude campaign`, for a Gemini Carbon launcher beside it (`Office Carbon campaign`, Google Antigravity on `gemini-4-carbon-medium`, following `.agents/rules/antigravity-runtime-and-safety.md`), and for both to carry the suite icon with the runner's badge, as the Isotone launchers do. `scripts/start-campaign.ps1` takes `-Runner claude|agy`; one launcher runs at a time whichever runner it starts. Claude Code starts on the latest Opus by alias (decision 30's verdict still names the model) at `--effort medium`, signed in with the one-year token; Antigravity uses its own account and never receives that token. A runner's mark is its company's trademark and is not kept in this public repository: `scripts/campaign-icon.py` draws it only from a file on the PC and otherwise leaves the badge its colour alone.
43. **A run starts only when the owner starts it (2026-11-12, replaces decision 21 and sharpens decisions 2 and 31):** closing the run's window stops it, and a crash or a reboot ends it. Nothing starts or resumes a session on its own: no scheduled task and no watchdog, and no automation in `.conclave/automations/tasks.json` is a campaign (the weekly digest and the like are not runs and stay). `scripts/start-campaign.ps1` starts the next session in its window only after a clean exit (exit 0) with the run still open; after a crash or any other exit it stops and says why. The launcher holds a Windows job object that ends every process the campaign started when the window's process goes, however it goes. The owner was asked whether the in-session heartbeat should go too and kept it: it is a timer inside the open session that nudges it when it goes idle after an API error or a stall, it cannot start a session and it dies with the window. Tests are never run from `pythonw.exe` or any other parent without a console on the owner's PC, since each child then opens a visible window; the launcher's tests start their processes with `CREATE_NO_WINDOW`.
44. **An app's sections are authored when its own inventory is done (2026-11-12, D03 T01 §30):** the owner said the product's sections for the shell and for Word should be written once the shell's and Word's inventories are done, and that it is not necessary to wait for all the inventory. An app's sections are authored when that app's inventory, its surface chapter with its signed-off mock-up, and the architecture decisions are done; nothing an app's authoring reads comes from another app's inventory. Guarantees that span all six apps (every record owned, every layout block equal to the inventory, a coverage report with no app missing, a disposition on every cloud-backed record, the six mock-ups compared) are proved at the ownership gate (D03 T01 §13), not before any app may start, and the checks behind them run from the day their tools exist, treating an app not yet captured or not yet authored as pending. The order follows from the plan's phases: the shell's and Word's inventory and chapters (Phase 2), the architecture decisions and the authoring of the platform, the engines and Write (Phase 3), their build (Phase 4, which Write joins), then the other five apps' inventories, chapters, authoring, the gate and their builds (Phase 5). Write is built first so that the platform, the authoring contract and the budget tests are proved on one app before they are applied to five more. Cost of reversing: the phase numbers and prerequisite lists `docs/specs/2026-11-12-per-app-authoring-design.md` names, and after Write's domain is authored the phase line of its sections.
45. **Test in proportion, and build while CI tests (2026-11-12):** the owner, watching a run in which more time went to full test runs and to waiting for CI than to building: "When we keep on adding tests and run full test suits on every implementation we are going to get to the point where we are testing 90% of the time and not progressing at all. There should be a balance or cadence between testing and implementation so that we progress as quickly as possible while retaining excellence." The cadence: a section runs the tests of what it changed while building and its affected test files before its stamp; the full suite runs in CI on every push and locally only at a phase closeout; a pending CI run does not hold the next row, which is built while CI tests, and a head still pending after 45 minutes is waited for; a section writes one test per promised behaviour and refusal. The owner added the same day: "CI status and monitoring it is still important; a red CI should be detected early and fixed", so every push is watched in the background from the moment it is made, and a red result is repaired the moment it arrives, before anything else is pushed. Unchanged: and a phase closeout, a draft release and the campaign's end wait for green. Measured on 2026-11-12 over two sections: about 50 minutes waiting for CI with the tree held clean and 30 minutes of local full-suite runs, against about 40 minutes of building. Cost of reversing: the pending bullet of `process-plan`'s CI watch and one Unattended rule.
