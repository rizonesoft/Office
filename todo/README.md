# TODO system: format spec

The `todo/` tree is the live execution plan for building the project. Markdown is canonical; `build/todo-cache.json` is a derived, gitignored projection. The one committed derived artefact is [`implementation-plan.md`](./implementation-plan.md), generated from the sections and never edited by hand.

One rule governs everything below: **a TODO section must be implementable by someone with zero conversation context.** A fresh session starts with none. If a section only makes sense to someone who was in the room, it is not done.

This system is Office's own, in its clean strict form: one validator that refuses malformed work, a generated plan, and stamps backed by review receipts. The governing product documents stay where they are: architecture and milestones in `docs/plans/`, the interface in `design/SPEC.md`. TODO files execute those documents; they do not restate them.

## Tree shape

```text
todo/
├── README.md               this file
├── TODO-00-INDEX.md        root index: domain order + active work
├── implementation-plan.md  generated by plan --sync; never edited by hand
├── plan.json               the plan's title, acceptance bar and phase names
├── findings.md             defects noticed while doing something else (file:line, unscheduled)
├── templates/              TODO-template.md (same file the create-todo skill carries)
├── 00-workspace/
│   ├── INDEX.md            domain index: every TODO in this domain
│   ├── TODO-01-<short-name>.md
│   └── TODO-02-<short-name>.md
└── 01-engine/
```

Domains are flat-numbered in allocation order and map to the foundation plan's milestones. Numbers are stable addresses: a new domain appends after the last one, because `DNN` cross-references encode them. Execution order lives in the dependency graph, not in the numbering.

Naming: `TODO-NN-short-name.md`, where `NN` is the next free number within that domain. Numbers are never reused. Renaming a file is safe: the stable `id` in frontmatter is what file-level references resolve against.

## Frontmatter

Every TODO file opens with YAML frontmatter, one scalar per line. Five required fields, four optional. That is the whole schema: resist adding more.

```yaml
---
schema_version: 1
id: example-runtime                # stable, kebab-case, globally unique, survives renames
domain: 01-engine                  # must match the containing directory
status: active                     # draft | active | blocked | done | superseded
title: "TODO-01 -- Example Runtime"
depends_on: ["repo-and-build"]     # optional: TODO ids that must fully ship first
frozen: true                       # optional: touches the frozen thread-safety contract
track: M1                          # optional: milestone reference
superseded_by: other-todo-id       # required with status: superseded
---
```

`id` rules: lowercase `a-z0-9-`, 2 to 60 chars, starts with a letter, no trailing dash. It must not change once other files point at it. Only `active` files produce ready sections. `done` is true exactly when every section is stamped (the last stamp sets it). A `superseded` file must name where its work went.

## File anatomy

In order: frontmatter, `# TODO-NN -- Title`, `> **Goal:**`, `> **Current state:**` (measured, dated, real paths), `## Inputs`, `## Outcome` (with the Adjacency line), `## Implementation Order`, the numbered sections `## 1.` to `## N.` in ascending order, and `## Verification` last. New sections go in numerical position, never after `## Verification`.

### The Implementation Order table is the dependency graph

Every `## N.` body section has exactly one row (`Order`, `§N`, `Deliverable`, `Depends On`, `[ ]`), and every row has exactly one body section. Keep every section heading (`## N. <Title>`) and its `Deliverable` cell (plus `Scope` cells in index tables) to a concise noun phrase of at most 88 characters so raw Markdown table rows stay at or under 100 characters (`MAX_TABLE_ROW`, as `AGENTS.md` requires) (with description cells <= 88 characters) and never wrap in raw `.md` view; put file paths, symbol lists, and flags in the section body and checklist. The validator enforces both directions, refuses `Deliverable` or section titles over 88 characters, refuses cycles, refuses a prerequisite in a later phase than its consumer, and refuses a ticked row without its stamp. A file holds at most 55 sections: past that, the next work opens a new file in the same domain, split by subject. Section numbers are permanent addresses and are never renumbered.

### Cross-reference notation

| Form | Means | Example |
| ---- | ----- | ------- |
| `§N` | Section N of this same file | `§3` |
| `TNN §N` | TODO-NN in the same domain, section N | `T02 §1` |
| `DNN TNN §N` | Domain NN, TODO-NN, section N | `D03 T01 §4` |

Never a bare number, and never a cross-TODO reference without a section. Cross-references in `-> XREF:` lines are bidirectional at file level: if this file points at `D03 T01 §4`, that TODO file must point back at a section in this file. The validator refuses one-sided XREFs and XREFs that name no real section.

### What every section declares

- `**Phase:**` from the closed list: 0 to 7 or 99 (Manual, operator only). The phase drives plan ordering; changing one is a scope decision. The project names its phases, the plan's title and its acceptance bar in `todo/plan.json` (`{"title": ..., "acceptance": ... or null, "phases": {"0": "<name>", ...}}`); `validate` and `plan` refuse unknown keys or phase numbers.
- `**Needs:**` `none` or a comma-separated list from: `windows-host`, `arm64-host`, `display-session`, `office`, `libreoffice`, `store-account`, `attended`, `owner-decision`, `third-party`, `operator`. `owner-decision`, `third-party` and `operator` hold the section out of `query ready` until the answer is recorded and the Need is removed. Unattended runs never take an `attended`, `store-account` or `operator` section.
- `**Surface:**` `yes` or `no`. A `yes` section builds or changes a user-facing surface and also carries four lines: `**Fidelity:**`, `**Job:**`, `**Treatment:**`, and `**Chrome:**`.
- `**Freeze check:**` in every section of a `frozen: true` file, and nowhere else.
- `**Build order:**` numbered steps, each naming a path, class, command or artifact in backticks and an observable `Done when:`.
- A checklist of 1 to 30 micro-step items, `- [ ] Commit: <message>` last. One item is one buildable step: one action, a named path or symbol in backticks, a `Done when:` observable end state in the same bullet, a `Cheaper substitute:` on UI and write items, and a source citation when behavior is copied from the SPEC, the foundation plan, or upstream specifications.
- `**Test checkpoint:**` a runnable command in backticks with its expected result. It must be able to fail.

Do not rewrite a `[x]` section's checklist: that is the contract its stamp covers. New granularity on shipped work is a new section.

### Micro/small items and 100% complete development plan

- **Small, single-responsibility sections:** Never bundle multiple subsystems, dialogs, or workflows into one coarse umbrella section. Split work into small, single-responsibility sections that each deliver one coherent capability, with explicit `Depends On` edges in the Implementation Order table.
- **Short table descriptions (`<= 88` chars):** Every `Deliverable` cell and `## N. <Title>` heading is a short noun phrase (`<= 88` chars, enforced by `validate`) so raw `.md` table rows in `TODO-*.md` and `todo/implementation-plan.md` never wrap in the editor.
- **Granular micro-step checklist items (five-part rule):** Never write a 1-bullet or 2-bullet summary checkbox for an entire subsystem. Decompose every section into individual micro-step checkboxes (typically 4 to 15 micro-steps per section, max 30). Every non-`Commit:` item carries: (1) one action (never "do X and then Y"), (2) a concrete path, symbol, or command in backticks, (3) `Done when:` observable end state in the same bullet, (4) `Cheaper substitute:` on UI and write items so the checkpoint and reviewer fail on shortcuts or wrong-layer edits, and (5) a source citation when copying behavior.
- **100% complete development plan:** Running `process-plan` to completion must leave a 100% complete, shippable product. Every milestone commitment in the foundation plan and every screen, dialog, control, command, setting, error/refusal path, undo/reverse operation, and persistence read-back in `design/SPEC.md` is owned by a concrete section and micro-step. Never cap operator-requested planning and never silently drop scope.
- **Surface completeness (`Surface: yes`):** Every control, menu item, dialog, and state on the SPEC surface is either working (proven on the rendered surface with real data and read-back) or deferred to a named, resolving section (`-> XREF: DNN TNN §N`). A disabled or stubbed control with no resolving owner section refuses validation and review.
- **Logical step commits:** Commits follow logical steps within a section; a section may land in one or more step commits, and review fix-loop commits append to the candidate range without amending.

### Brownfield code and incomplete TODO trees

When adopting or grooming this system on a repository where code is already partially implemented or the `todo/` tree is incomplete:

- **Already-stamped `[x]` sections are never rewritten:** Their checklist is the historical contract covered by their receipt. If a `[x]` section was coarse or left gaps, keep it untouched and file the missing work as a new `## N.` section in numerical order with `-> XREF:` back to the original section. If a `[x]` section's `Test checkpoint` no longer passes, or its own `Done when:` was never met, `review-todo-section` in audit stance files the repair and reopens it with `todo-graph.py unstamp`.
- **Open `[ ]` micro-steps already implemented in code:** During `groom-plan` or `process-todo-section` Step 2/3, verify the existing code against the micro-step's `Done when:` and `Cheaper substitute:`. If 100% satisfied, `groom-plan` appends `Already shipped: <commit SHA or file:line>` and leaves it `[ ]`; `process-todo-section` re-verifies it and ticks it when it runs the section. If only partially implemented (for example, happy path exists but refusal path, token binding, or test is missing), leave it `[ ]`, update `> **Current state:**` to name what exists, and decompose the remaining work into concrete micro-steps.
- **Open `[ ]` section already 100% implemented in code:** Do not churn working code just to manufacture a diff. Verify every micro-step's `Done when:`, add any missing falsifiable test if the checkpoint cannot fail, run the `Test checkpoint` for real, commit the ticked checklist and verification evidence, and run `review-todo-section` plus `stamp` against the implementing or verification commit SHA.
- **Features already in the codebase with no TODO file:** Features that are already 100% complete and tested in the baseline codebase are recorded in `> **Current state:**` of the relevant domain's TODO file; features that are incomplete, untested, or stubbed get small single-responsibility sections and five-part micro-steps for the remaining work so (`baseline code` + `open plan`) equals a 100% complete product.

### Adjacency: the surfaces a file owes beyond its record

`## Outcome` carries one executable `**Adjacency:**` line. Write every key exactly once, separated by semicolons: `key=applicable`, `key=applicable @ DNN TNN §N` for an explicit owner, or `key=not-applicable (reason)`. A narrow non-feature file may declare `all=not-applicable (reason)`. The nine keys: `list` (find a record without its identifier), `document` (what a user carries, sends, prints or files), `settings` (every tunable, with a named consumer), `reporting` (summaries and exports over the domain's data), `notifications` (lifecycle notices with recipient rules), `permissions` (refusals exercised, both ways), `audit` (who changed what, and the diagnostic trail), `exchange` (import and export), `reverse` (the undo of every create: cancel, reopen, revert). "Not applicable" is a declaration with a reason, not silence. Owner references must resolve; `python scripts/todo-graph.py query adjacency` prints every declaration. An `**Adjacency rationale:**` paragraph under the line records the substantive decisions for human review.

## Stamps and receipts

A section closes only through `stamp`:

```powershell
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <full 40-char implementation commit> --review '1:docs/reviews/01-engine/D01-T01-s1.md:clean' --completion docs/reviews/01-engine/D01-T01-s1-completion.md --check '<command> -> <quoted result>'
```

`stamp` refuses unless every checklist item except `Commit:` is ticked, every prerequisite is stamped, no waiting Need remains, the SHA is a full commit on this branch, at least one review round (`clean`, `fixed` or `stopped-at-33`; `stopped-at-22`, `stopped-at-13`, `stopped-at-8` or `stopped-at-3` on receipts from earlier caps; with the findings file as its report), at least one check, and `--completion` naming the section's completion record (`docs/reviews/<domain>/D<NN>-T<NN>-s<N>-completion.md`, written before the build by `process-todo-section` from `docs/completion-review-prompt.md`, with every gap of its last returned round extended or filed) are given. Adoption (owner decision 2026-10-23, D00 T03 §13): a section whose review loop began before the 33-round cap and the completion review existed (D02 T01 §23 in `docs/phase-runs/2026-10-22-phase-2.md` is one) continues under the 33-round cap, and before its stamp runs one completion review of its contract; because its code already exists, every gap is filed as a new section through `add-todo` rather than extended. A section reopened by `unstamp` needs a fresh completion review, run after the reopening, before it stamps again. A `stopped-at-33` verdict, or `stopped-low-severity` (from round 9 on, a round with only `P3` or advisory findings, declared by the reviewer as `HIGHEST: P3`, ends the loop and its findings are filed), also needs `--cap-outcome` saying what was done. The receipt records `rounds_spent`, `round_cap` (and `cap_outcome`) and `completion`; `query rounds` summarises them. It then writes the receipt `docs/reviews/<ref>.json`, ticks the `Commit:` item and the Implementation Order row, appends the stamp at the end of the section, and marks the file `done` when its last section stamps, all or nothing.

An audit that finds a stamped section regressed reopens it only through `python scripts/todo-graph.py unstamp '<ref>' --reason '<what regressed; repair -> XREF: <ref>>'`: it removes the two stamp lines, unticks the `Commit:` item and the row, reopens the file, keeps the receipt as `docs/reviews/<ref>.revoked-<date>.json`, adds `> **Unstamped:** <UTC instant>: <reason>` to the section (`--at`, default now; D00 T03 §14) and syncs the plan, all or nothing. The section then re-stamps with a fresh receipt, on a completion review run after that instant (a date-only note from before D00 T03 §14 counts as the end of its day). From `CONTRACT_REQUIRED_FROM` in `scripts/lib/todo_graph.py` on, a completion reply also opens with `CONTRACT: sha256:<digest>`, copied from its prompt (`python scripts/todo-graph.py contract-digest '<ref>'`), and `stamp` refuses a section whose contract changed after that round, or whose last returned round still has an `extended` gap. Receipts record `completion_rules` (D00 T03 §16): every stamp writes `2` and must meet those rules whatever its review's date, a re-stamp after `unstamp` included; a stored receipt without the field is version 2 when its completion review ran from `CONTRACT_REQUIRED_FROM` on and version 1 before, and validation holds a version 2 receipt to the contract it was reviewed on while a version 1 receipt keeps the D00 T03 §13 rules. Old reviews are never rewritten to add a digest. A deferral is closed by changing only its marker, `Deferred:` to `Resolved:`, which keeps the contract digest, so the deferring section's receipt survives.

## Commands

```powershell
python scripts/todo-graph.py validate            # structure + graph integrity; exits 2 with the reason on any fault
python scripts/todo-graph.py build               # parse todo/ -> build/todo-cache.json
python scripts/todo-graph.py render              # mermaid dependency graph
python scripts/todo-graph.py plan --sync         # regenerate todo/implementation-plan.md after any edit
python scripts/todo-graph.py plan --check        # fail if the generated plan is stale (CI runs this)
python scripts/todo-graph.py query ready         # sections that can run now (also: blocked, stats, deferred, adjacency, plan, rounds)
python scripts/todo-graph.py resolve 'D01 T01 §1'  # 0 ready, 1 no such section, 2 no reference, 3 verified, 4 waiting
python scripts/todo-graph.py classify 'D01 T01 §1' 'D02 T01 §1'   # dispositions as JSON
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <commit> --review '1:<report>:clean' --completion <completion record> --check '<cmd> -> <result>'
python scripts/todo-graph.py unstamp 'D01 T01 §1' --reason '<what regressed; repair -> XREF: <ref>>'
python -m unittest scripts.tests.test_todo_graph   # the tooling's own tests
```

## Skills

| Skill | Use |
| ----- | --- |
| `add-todo` | Route new work to the right domain, file, and section. |
| `create-todo` | Author a new TODO file, wire XREFs, and update indexes. |
| `groom-plan` | Harden sequence, drift, gaps, and micro-step granularity. |
| `process-todo-section` | Fact-check, repair drift, and ship exactly one section. |
| `review-todo-section` | Run review lenses and write the stamp via `stamp`. |
| `process-todo-file` | Run loose-end sweep and close an all-`[x]` file. |
| `process-phase` | Repair, gap-audit, and run a phase to 100% or park it. |
| `process-plan` | Front door for `implementation-plan.md`; chains phases. |

## Rules for every file

- One line per paragraph and per list item in Markdown prose; no em dashes or en dashes in new text; keep Markdown table description cells at or under 88 characters so they do not wrap in raw `.md` view.
- A defect noticed outside the current work is filed in `todo/findings.md` with `file:line`, not fixed on the side inside someone else's commit; scheduling it means writing a section through `add-todo`.
- Questions that need a person are not TODO rows without a Need: the section names `owner-decision` or `third-party` and records the answer before the Need is removed.
