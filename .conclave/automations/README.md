# Office automations

Every scheduled job for Office lives here: the task list in `tasks.json`, the runner, the failure alert, and the Task Scheduler installer. Ported from Isotone's automations (operator request, 2026-10-20), which were adapted from Rizonetech's; Office runs on Windows, so the tasks are Windows Task Scheduler tasks under `\Office\`.

## What runs

| Task | When (local time) | Runs |
| --- | --- | --- |
| `office-owner-digest` | Monday 07:00 | `scripts/owner-digest.py` |
| `office-owner-digest-retry` | 5 minutes after logon, then every 6 hours | `scripts/owner-digest.py --retry` |
| `office-visual-studio` | Monday 07:25 | `scripts/check-visual-studio.py notify` |
| `office-python-pin` | Monday 07:30 | `scripts/check-python-pin.py notify` |
| `office-pr-merge` | Daily 07:43 | `scripts/merge_prs.py --skip-unsafe` |

What each one tells you about, and when it fails (which records a failure notice instead):

- `office-owner-digest`: emails the owner's weekly digest (decision 32 of `docs/specs/2026-10-23-campaign-scope-design.md`): the state of the run and of CI, the plan's totals, every section waiting on the owner with its `**Owner action:**`, ordered by how much waits behind it, and the sections verified since the last digest that was delivered: the period starts on the last day the previous delivered digest covered (seven days back for the very first), stays where it was through every failed attempt, and reaches back to any period SMTP2GO's log later shows never left, so a failed week is reported with the next one (D00 T07 §3). A list too long for the 120-line body is cut at whole entries and goes whole in an attachment: `waiting-on-you.txt` for the waiting list, `verified-this-week.txt` for the verified sections (D00 T07 §2). `python scripts/owner-digest.py --dry-run` prints it. Fails when the TODO tree cannot be read (exit 2) or the send is refused (exit 1).
- `office-visual-studio`: records a notice once per release when this machine's Visual Studio 2026 (the MSVC toolset the C++ build uses) is behind its latest servicing release. Fails when none is installed, or vswhere or the release channel cannot be read.
- `office-python-pin`: records a notice once when this machine's Python is behind the newest stable CPython (minor or patch). Fails when python.org cannot be read.
- `office-owner-digest-retry`: sends again a digest that surely did not go out (SMTP2GO refused it, or it failed before anything was sent), or one SMTP2GO's log later shows never left, and a weekly digest that could not go out because the day's sends were spent; at most four sends a day, the weekly one included, counted in `build/automations/owner-digest.json`. A send that may have gone out (a timeout, a cut connection) is never sent again before SMTP2GO's log settles it. With nothing failed it sends nothing and changes nothing (D00 T07 §3).
- Every task restarts after a failed launch (D00 T07 §4): `task-settings.ps1` gives each one Task Scheduler's own restart on failure, three more attempts ten minutes apart, so a launch that fails before `run.py` starts (2026-11-09: result 0x8007010B twice, two minutes after Windows logged that it was out of virtual memory) is tried again. `pwsh .conclave/automations/check-task-retry.ps1` proves it on this PC with a scratch task whose working directory does not exist, and removes that task afterwards. A task that never reaches `run.py` writes no log under `build/automations/`, so the weekly digest asks Task Scheduler itself and names any listed task whose last result is a failure or that is not installed; Task Scheduler's own log of launches is off by default, and `install.ps1` says whether it is on and prints the command that turns it on from an elevated window.
- `office-pr-merge`: records nothing on success; merges green Dependabot and pins pull requests (labelled `dependencies` or `pins`, every check green, cleanly mergeable) one at a time by rebase, then pulls and validates. It skips quietly (exit 0, the reason in its log) while a campaign run is open (the campaign merges at its own section boundaries) or while the checkout is dirty, off `main`, behind or ahead of `origin/main`, or mid-section. Each pull request is read again and judged again just before its merge, under the run guard's lock. Fails when a merge, pull or validate fails (exit 1), leaving the rest open (a pull request already merged when its pull or validate failed is reported as merged), or when git or gh cannot be run or read (exit 3).

Every task starts when available: a run missed while this PC was off fires at the next chance. A start while the task still runs is ignored, the execution limit is five minutes past the task's timeout, and daily and weekly tasks carry a five-minute random delay. Tasks run only while the operator is logged on, so no password is stored. Everything in this folder is Office's own, for the fixed-time daily trigger and the per-run alert record. Office takes nothing from the Conclave SDK (operator, 2026-10-21): the `office-conclave-kits` drift check and `.conclave/kits.json` were removed that day.

## How you hear about it

One email a week, and no other (decision 32 of `docs/specs/2026-10-23-campaign-scope-design.md`; D00 T03 §53): the Monday digest, "Office weekly: N waiting on you, M verified this week (id)", to `rizonetech@gmail.com` from "Office automations" (`website@rizonetech.com`, through SMTP2GO). Everything else that you need to hear about is a notice, recorded in `build/automations/notices.jsonl` by `alert.py` (`record_notice`, or `python .conclave/automations/alert.py --notice <subject> <body file>`), and the next digest lists the pending ones after what is waiting on you, one line each, with every notice in full in the attached `notices.txt`; the batch is claimed before the send and marked once that digest was delivered, never by `--dry-run` or a refused send. A claim no digest confirmed (a mark that failed after the send, a run that stopped mid-send) is settled against SMTP2GO's activity log at every scheduled run, daily through `office-pr-merge`: a digest the log shows delivered is marked and its notices are never sent again; one it shows rejected or bounced, or does not show at all, is sent again in full by the next digest; while the log cannot be read or shows the email still in flight, the claim is kept and asked again the next day. Each digest's subject ends with its own short id, so the log's answer is about that one email. A notice an earlier digest did not deliver is marked so when it is sent again. A digest that SMTP2GO accepted also writes that fact to a second store under the scratch folder (`office-digest-evidence`, outside the repository's volume) before it marks its batch, so a mark that fails can never make it repeat. Within SMTP2GO's history the log alone decides, so a bounce that arrives late is still seen; the record counts only once the log can no longer decide. A claim with neither (a run cut off mid-send) still undecided after five days, when SMTP2GO's free plan no longer keeps its activity, is the one case with no evidence either way: the next digest says so in one line ("could not be confirmed delivered") and carries each such notice in full in `notices.txt` under a heading saying it may already have reached you, so none is lost and the only possible repeat is labelled. `alert.py --list` prints every notice no digest has completed, pending, claimed or unconfirmed, with its text.  The senders, all waiting for Monday:

- **`run.py`**, "Office automation failed: <task> on <host>": a scheduled task exited non-zero or timed out, with the tail of its log. It is recorded on every failing run until fixed.
- **The host check** (`scripts/check-campaign-host.py --notify`), "Office: campaign host not ready on <host>": every failing check with its fix.
- **The version checks** (`scripts/check-visual-studio.py`, `scripts/check-python-pin.py`), "Office: ... is available": something on this PC is behind. The task succeeds and records this once per new version or state.
- **The pin proposals** (`pin_proposal.propose`), "Office: ... is ready to merge": a pin moved on a branch from main after its checks passed; the notice names the branch and the `git merge` command. Nothing changes on main or in your checkout until you merge, and nothing is pushed. No task proposes pins today; the C++ toolchain pins (D00 T03 §11) will.
- **The campaign** (`process-plan`), "Office campaign parked: ...": a host that is not ready or a CI run that stayed red parked the run, with the fixes.

Each new version or state is recorded once, so no new notice means nothing new, not that every pin is current: a proposal you have not merged stays on its branch without another notice, and a machine finding you have not acted on is not recorded again. `python scripts/check-<name>.py check` (exit 1 while main is behind or this PC needs an update) and `git branch --list "pins/*"` show what is still open. Each finished proposal and announcement is a git ref (`refs/office-pin/<key>`, `refs/office-notice/<key>`), written only after its notice is recorded; `git for-each-ref refs/office-pin refs/office-notice` lists them, and deleting one makes its task propose or announce again. A proposal branch without its ref is an unfinished attempt (a notice that could not be recorded, a run cut short), which the next run discards and redoes. The shared code is `scripts/lib/pin_proposal.py` and `scripts/lib/pin_sources.py`, ported from RectoPDF on 2026-10-21.
## Campaign runs

There is no keep-alive task. Retired 2026-10-21 (operator: "we do not need the keep-alive in automations, just heartbeat with stop hook"): a `process-plan` run is held by the run guard alone, the Stop hook (`scripts/campaign_guard.py stop-hook`, wired in `.claude/settings.json`) and the in-session `CronCreate` heartbeat. Both live inside the session and die with it. No task here starts or resumes a campaign session, and none may be added: a run starts only when the owner starts it, closing its window stops it with everything it started, and a crash or a reboot ends it (owner, 2026-11-12; decision 43, which replaces decision 21). Inside its window the launcher starts the next session only after a clean exit; a session that crashed is not started again. The owner starts the launcher again to carry on, and the new session takes the guard with `acquire --handover`. The `process-plan` skill holds the rules. The operator starts or resumes a campaign with `pwsh scripts/start-campaign.ps1`, or the desktop shortcut that `pwsh scripts/start-campaign.ps1 -InstallShortcut` writes for this clone: it runs the host readiness check, then opens Claude Code without permission prompts and with its `/goal` set to the finished plan. The launcher signs the session in with the one-year token from `claude setup-token`, read at start from the repository's own untracked env file, `.secrets/office.env`, into `CLAUDE_CODE_OAUTH_TOKEN` for that process only and never printed. The file is filled once by `python scripts/import-secrets.py` from the Conclave vault item "Claude Code OAuth token (1 year, setup-token)" (owner, 2026-11-10: the repository is self-contained, and the token is stored on this PC's disk in that file); the launcher itself never reads the vault or runs the import. When the file holds no token it says so, names the command, and the session uses the interactive sign-in. The owner stops a run by asking the session to stop cleanly, or with `pwsh scripts/start-campaign.ps1 -Stop` (there is no Stop shortcut; owner, 2026-11-11): `-Stop` writes `build/campaign-stop-request`, which the campaign honours at its next section boundary and which the launcher checks before every session it would start; answering NOW also ends the running launcher and everything it started. Starting again removes the request.

## When a run fails

Task Scheduler starts `pythonw.exe .conclave/automations/run.py <name>`. The runner writes the run's output to `build/automations/<name>/<UTC>.log` (the newest 20 kept) and its outcome to `build/automations/<name>/last.json`. On a non-zero exit or a timeout it records a notice through `alert.py` for the Monday digest: the task, its exit, and the tail of that run's log.

- The digest that reports it sends through SMTP2GO from `website@rizonetech.com`, the verified sender the Rizonetech automations use (Rizonesoft is a brand of Rizonetech).
- The key is read at send time from the repository's own untracked env file, `.secrets/office.env`, which `python scripts/import-secrets.py` fills from the Conclave vault item "Rizonetech SMTP2GO (website mail)" (owner, 2026-11-10: the repository is self-contained). Nothing reads the vault at send time: on a clone that has not imported yet a send is refused with that command, and the failure is in the task's log. `python scripts/import-secrets.py --check` says whether the key is present.
- SMTP2GO answers a refused send with HTTP 200 and `succeeded: 0`; the alert treats that as a failure.
- The runner exits with the command's code (124 on a timeout), or 3 when the notice could not be recorded, with the reason appended to the run's log, so Task Scheduler's Last Run Result shows every failure.

## Install and inspect

```powershell
pwsh .conclave/automations/install.ps1              # idempotent; re-run after editing tasks.json
pwsh .conclave/automations/install.ps1 -DryRun      # print what would be registered or removed
pwsh .conclave/automations/install.ps1 -Uninstall   # remove every \Office\ task
Get-ScheduledTask -TaskPath '\Office\' | Get-ScheduledTaskInfo | Format-Table TaskName, NextRunTime, LastRunTime, LastTaskResult
python .conclave/automations/run.py <name>                    # run one task in this console
python .conclave/automations/alert.py <name> --dry-run        # preview the alert for its last run
python -m unittest discover -s scripts/tests -p "test_automations.py"
python -m unittest discover -s scripts/tests -p "test_pin_automations.py"
git for-each-ref refs/office-pin refs/office-notice           # finished proposals and sent notices
```

## Adding an automation

1. Add an entry to `tasks.json`: an `office-` name, a description, the command (a script in this repository, `python` first), a trigger (`{"daily_at": "HH:MM"}`, `{"weekly": "<Day>", "at": "HH:MM"}` or `{"at_logon_delay_minutes": N, "every_minutes": N}`), and `timeout_minutes`.
2. Add its row to the table above and its line to the list under it; `scripts/tests/test_automations.py` fails until the table and the file agree.
3. A check that moves a repository pin proposes it through `pin_proposal.propose` (a branch from main, checks, a notice); a check of something on this PC announces it through `pin_proposal.notice` (one notice per new version or state). Neither changes main or the checkout. Add its tests to `scripts/tests/test_pin_automations.py`.
4. Run the tests, then the installer.
