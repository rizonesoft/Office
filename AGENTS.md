# AGENTS.md

This repository builds **Rizonesoft Office**, an open-source (GPL-3.0-or-later) Windows office suite in planning and design, whose six apps are to match their Microsoft counterparts feature by feature: Write (Word), Grid (Excel), Stage (PowerPoint), Flow (Visio), Plan (Project) and Mail (Outlook). The names and identifiers are recorded in `docs/brand/NAMES.md`; the plan is `todo/`; brand and icon sources are `scripts/lib/` and `design/`, with generated outputs in `assets/`. The verification commands are `python scripts/todo-graph.py validate`, `python scripts/build-icons.py --check` and `python scripts/run-tests.py` (the test files of `scripts/tests` side by side; `python -m unittest discover -s scripts/tests` runs the same tests serially), all run in CI (`.github/workflows/ci.yml`). Claude Code (the main session, the latest Opus started by alias in `scripts/start-campaign.ps1`, which writes the code itself; no agent writes) is the only writer and the one Codex reviewer `.conclave/reviewers.toml` routes to the only reviewer (owner decisions 2026-10-23; the pin, not this file, names it). The review tooling (`scripts/review-dispatch.py`, `scripts/review_pin.py`, `scripts/review-prompt.py`, the four prompts in `docs/` and the `independent-review` skill) is the Conclave SDK's reviewer kit, imported on 2026-11-11 (owner decision, which ends the 2026-10-23 rule that the repository takes nothing from the SDK); the copies here are the repository's own and are changed here.

## Product bar

We are building a better product than Microsoft's, not a clone (owner, 2026-10-23). Parity is the floor; every feature is optimised and improved, beats Office's measured times on the same PC, and never takes a shortcut where the harder, better version is possible. The rules a plan, a build and a review check are in [docs/product-principles.md](./docs/product-principles.md).

## Autonomy

Act as the owner would, and better (owner, 2026-11-10; [docs/product-principles.md](./docs/product-principles.md)): decide what can be worked out and record it, improve the plan, skills, agents, runners, tools and methods as part of the product, repair the run's own failures at their owning layer with a test, and never plan less because something is hard or no competitor does it. Ask only for what the owner alone holds: a credential, a legal signature, money, or something that cannot be undone. A question whose answer the session can work out is never asked (owner, 2026-11-11): when one option can be named as the recommendation, take it, record the decision and what reversing it costs, and carry on. No competitor sets the ceiling, whether Microsoft, Adobe, Apple or Google: where they are good we are measurably better, and "nobody has done it" is a reason to plan the work, never to drop it.

## Working rules

- Verify files, routes, schemas, tools, and commands before relying on them. A path someone mentions is a hypothesis until it is on disk.
- Inspect existing patterns, imports, the package manager, the framework, and the test commands before editing. Do not infer architecture or tool schemas from memory when the repository can answer.
- Resolve a tool by capability before path. Prefer explicit config, then discovery, then a setup-required state. Store discovered paths only in ignored local config and never hardcode user-specific absolute paths.
- Build tools are repo scoped and portable (owner, 2026-11-10): CMake, Ninja, sccache, vcpkg and the LLVM tools are fetched at pinned versions and hashes (`tools.lock.json`) into the ignored `.tools/` folder inside the clone by `python scripts/bootstrap-tools.py` (D00 T04 §1), and used from there, never from a machine install or `PATH`: a script asks `tool_path()` and `tool_env()` in `scripts/lib/tool_lock.py` (D00 T04 §2), which refuse rather than fall back. Visual Studio's MSVC toolset and the Windows SDK cannot be carried and stay host prerequisites. Other tools (Python, Git, `gh`, the agent CLIs) are user-level installs; add repo-scoped wrappers where they encode project-specific behavior or reproducible commands.
- Real data only. Demo or seed data stays behind an explicit demo mode and is labeled as such.
- Develop straight on `main` (owner, 2026-11-10, reaffirmed the same day after branches for our own work were briefly allowed): no feature branches, no worktrees and no pull requests for our own work; commit to `main` and push. The only branches are the ones outside tools make by themselves (`pins/*` proposals, Dependabot, short-lived CI proof branches). Work that needs a second copy of the tree (a measurement, a parallel stream) uses a separate clone under the scratch folder, whose only branch is its own `main`; its commits reach this repository's `main` by being replayed onto it, never by a merge of a named branch, and the clone is deleted when its job ends or reused when the job recurs. `git branch -a` and `git worktree list` therefore show `main` and the tool branches only.
- Run the relevant typecheck, lint, and tests after a change.
- Fix at the owning layer: a setting in its setting, behaviour in the code that produces it, data in the data. No output filters that hide a problem. Code changes end the report with a `Layer:` line.
- Markdown prose is never hard-wrapped: one line per paragraph and per list item. Every Markdown table row stays `<= 120` characters (owner, 2026-11-10; it was 100).
- Never use em dashes or en dashes anywhere: prose, code, comments, commit messages and generated files.
- Temporary files and full logs go to scratch, never the repository: the folder the `OFFICE_SCRATCH` environment variable names (on the owner's PC `R:\scratch`, which WSL sees as `/mnt/r/scratch`), or the session scratchpad when one is given. Code never writes a machine's path: a tool finds the repository from its own location, scratch through `OFFICE_SCRATCH` (falling back to the system temporary folder), and a program through `PATH`, `vswhere` or an environment variable; `scripts/tests/test_no_hardcoded_paths.py` fails on a drive, home or mount path in a tool. A `R:\scratch\...` path in a TODO section means that scratch folder, and the code built from it resolves it.

## Safety

- Local reversible work in the repository needs no confirmation.
- Ask the operator once before anything that sends, deletes, or changes something outside the repository: mail, production systems, cloud changes, SQL writes, dropping data, credentials.
- When a command needs sudo, give the operator the exact command to run with `! sudo ...`. Never store the sudo password.
- Never print, log, or commit a secret value.
- The repository is self-contained for credentials (owner, 2026-11-10): `python scripts/import-secrets.py` copies each credential named in `scripts/lib/secret_store.py` from the Conclave vault into `.secrets/office.env` in the clone (ignored by git, closed to every other user account), and code reads a credential only through `secret_store.get`, never from the vault, WSL or an environment variable of the machine. A new credential is added to `SECRETS` there with its vault item and its shape; `python scripts/import-secrets.py --check` says which are present, by name only.
- Green dependency pull requests merge by themselves (owner decision 2026-10-21): `scripts/merge_prs.py` merges Dependabot and pins pull requests that are labelled `dependencies` or `pins`, have every check green and leave the C++ toolchain pin files (`vcpkg.json`, `vcpkg-configuration.json`, `CMakePresets.json`) alone, one at a time by rebase, at a campaign section boundary or through the `office-pr-merge` task, and never into a dirty, unpushed or mid-section clone. Local pin proposal branches (`pins/*`) still wait for the owner's merge.

## Subagents

- The lead is one long session on the model `.conclave/operating-mode.json` names, the verdict `python scripts/measure-modes.py decide` stores from a measurement (owner decision 30: measured, never chosen; D00 T03 §36 and §37), which the launcher reads at each start; the first verdict, from the measurement recorded in `docs/reviews/operating-mode-2026-11-10.md`, is the latest Opus. Whichever model it is, the lead writes everything itself, the hard fixes and the architecture decision records included, with only the Sonnet readers below beside it. The lead is the only writer (owner, 2026-11-11, who follows the development in the main session): it decides, plans, builds every section, every round of review fixes and every architecture decision record itself, runs the gates and the review loop, triages findings and commits. No agent writes: the Opus `section-writer` and the Fable `principal-implementer` were removed on 2026-11-11, and `scripts/verify-agent-tiers.mjs` refuses any agent that holds an edit tool. Work goes to:
  1. A script, for anything with one right answer (validate, sync, stamp, scaffolding, path checks, generated blocks). Mechanical work done twice by a model becomes a script.
  2. The Sonnet readers below, for finding facts, running suites and proving tests can fail. No agent writes.
  3. The lead itself: every build, every round of review fixes, plan corrections, the triage of review findings, and anything outward or irreversible.
  - Haiku is retired (owner, 2026-11-10): no agent pins a Haiku model. What it was allowed for is a script's job.
  - Effort ceiling (owner, 2026-11-10): a Sonnet agent never runs above `high`, whether the effort comes from the definition's `effort:` field or from the call.
- A review loop that will not converge is the lead's to re-think, not to hand off: after round 8 with a `P1` or `P2` finding still open, or at any round when a finding reported fixed comes back, the lead stops patching, names the cause the rounds share, checks every open finding against the section's purpose (a finding about a case the repository does not have and the section does not promise is recorded as out of scope, not owed), and rebuilds the unit that keeps failing.
- Claude subagents pin an explicit `model:`, Sonnet for every reader.
- Every agent reads and runs. Every Claude subagent declares an explicit `tools:` list, never `*`, without Edit, Write, MultiEdit or NotebookEdit. No agent declares `memory:`, because Claude Code then enables Write and Edit whatever the `tools:` list says.
- An agent that gets its job wrong is removed, not kept and watched (owner, 2026-11-10: quality matters more than delegation). When the main loop's own check shows an agent returned a wrong fact, a wrong result or a claim it did not verify, delete its definition from `.claude/agents/`, its entry in the fleet list below and its lines in the Delegation sections of the skills, in one commit that says what it got wrong, and do that work in the main loop from then on. An agent that only failed to run (a timeout, an empty reply) is not removed for that.
- Run `node scripts/verify-agent-tiers.mjs` after adding, changing or removing an agent definition; it enforces these rules.
- The fleet is `.claude/agents/`: `code-explorer` (locate and map code), `git-runner` (history and diffs), `test-runner` (suites and gates, full log to scratch), `mutation-tester` (prove a test can fail), `debug-evidence` (facts about a failure), and `source-researcher` (primary-source facts with URLs), all Sonnet readers. Which step hands what to whom, and what the main loop still checks itself, is the Delegation section of `process-todo-section` and of `review-todo-section`.

## Code intelligence

- Claude Code loads two language servers through the plugins enabled in `.claude/settings.json`: `pyright-lsp` for the Python tooling (configured by `pyrightconfig.json`, on which `pyright` reports 0 errors today) and `clangd-lsp` for C++. Use the `LSP` tool for definitions, references and call hierarchies before text search, and read the diagnostics it reports after an edit.
- Each needs its server on `PATH`, installed per user and never into the repository: `uv tool install "pyright[nodejs]"` gives `pyright-langserver`, and `clangd` is the pinned one in `.tools/`, installed by `python scripts/bootstrap-tools.py` (D00 T04 §1). The campaign launcher (`scripts/start-campaign.ps1`) puts the tool folders first on the session's `PATH` and, when the pinned `clangd` is missing, starts the session with the `clangd-lsp` plugin switched off, so it never uses a machine copy (D00 T04 §4); a session started any other way runs `python scripts/bootstrap-tools.py --bin-dirs` and puts those folders first on its `PATH`. A clone installs the plugins once with `claude plugin install pyright-lsp@claude-plugins-official --scope project` and the same for `clangd-lsp`.

## TODO workflow

Plan and build through the TODO system: [docs/todo-workflow.md](./docs/todo-workflow.md).

- Every clone runs `git config core.hooksPath scripts/hooks`: its pre-commit hook refuses a TODO change committed without `python scripts/todo-graph.py plan --sync`.
- A section takes three review passes (owner decision 2026-11-11), each through `scripts/review-dispatch.py` to the one reviewer `.conclave/reviewers.toml` pins, at the effort and lenses the pin's `[schedule]` sets: a plan review before the build (`docs/plan-review-prompt.md`, `process-todo-section`), one round after it carrying every defect lens, and one completion review of the final candidate (`review-todo-section`). A completion that returns a `P1` or `P2` gap is repaired and followed by a reconciliation, up to 33 returned passes per section; a pass whose worst finding is `P3` is filed as new sections and takes no further pass. `stamp` replays the schedule over every recorded pass and refuses a section whose passes are missing, out of order or run at another effort or lens.
- Sections stamped before 2026-11-11 keep their receipts (a pre-build completion record and up to 33 rounds): `docs/reviews/legacy-receipts.json` freezes each by digest, so they stay valid and no new receipt can take their shape.
- Tests: CI runs the whole suite on every push, in four parallel shares (`python scripts/run-tests.py --shard <i>/4`, which also reproduces a red share on this PC; owner, 2026-11-12, decision 45: this PC runs the tests a change touches, GitHub the rest). The whole suite on this PC is `python scripts/run-tests.py`, needed only to reproduce a red run or to record durations (`--record-durations`), and queued as `bosun run -- python scripts/run-tests.py` (owner, 2026-11-12: full suites and full builds go through the machine's job queue; a single test file runs directly), or one file with `python -m unittest discover -s scripts/tests -p "test_<name>.py"` (agent tooling, TODO graph, run guard, automations and project scripts).
- Checks the CI `gates` job runs beside the tests, each runnable on its own: `python scripts/todo-graph.py validate`, `python scripts/todo-graph.py plan --check`, `python scripts/check-spdx.py`, `python -m reuse lint`, `python scripts/build-icons.py --check`, `python scripts/bootstrap-tools.py --check` and `python scripts/lessons.py check` (the lesson store of `docs/lessons/`, D00 T05 §1).
