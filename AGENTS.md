# AGENTS.md

This repository builds **Rizonesoft Office**, an open-source (GPL-3.0-or-later) Windows office suite in planning and design, whose six apps are to match their Microsoft counterparts feature by feature: Write (Word), Grid (Excel), Stage (PowerPoint), Flow (Visio), Plan (Project) and Mail (Outlook). The names and identifiers are recorded in `docs/brand/NAMES.md`; the plan is `todo/`; brand and icon sources are `scripts/lib/` and `design/`, with generated outputs in `assets/`. The verification commands are `python scripts/todo-graph.py validate`, `python scripts/build-icons.py --check` and `python scripts/run-tests.py` (the test files of `scripts/tests` side by side; `python -m unittest discover -s scripts/tests` runs the same tests serially), all run in CI (`.github/workflows/ci.yml`). Claude Code (the latest Opus as the lead, started by alias in `scripts/start-campaign.ps1`, with the Claude workers it delegates to) is the only writer and the one Codex reviewer `.conclave/reviewers.toml` routes to the only reviewer (owner decisions 2026-10-23; the pin, not this file, names it); the repository takes nothing from the Conclave SDK.

## Product bar

We are building a better product than Microsoft's, not a clone (owner, 2026-10-23). Parity is the floor; every feature is optimised and improved, beats Office's measured times on the same PC, and never takes a shortcut where the harder, better version is possible. The rules a plan, a build and a review check are in [docs/product-principles.md](./docs/product-principles.md).

## Autonomy

Act as the owner would, and better (owner, 2026-11-10; [docs/product-principles.md](./docs/product-principles.md)): decide what can be worked out and record it, improve the plan, skills, agents, runners, tools and methods as part of the product, repair the run's own failures at their owning layer with a test, and never plan less because something is hard or no competitor does it. Ask only for what the owner alone holds: a credential, a legal signature, money, or something that cannot be undone.

## Working rules

- Verify files, routes, schemas, tools, and commands before relying on them. A path someone mentions is a hypothesis until it is on disk.
- Inspect existing patterns, imports, the package manager, the framework, and the test commands before editing. Do not infer architecture or tool schemas from memory when the repository can answer.
- Resolve a tool by capability before path. Prefer explicit config, then discovery, then a setup-required state. Store discovered paths only in ignored local config and never hardcode user-specific absolute paths.
- Build tools are repo scoped and portable (owner, 2026-11-10): CMake, Ninja, sccache, vcpkg and the LLVM tools are fetched at pinned versions and hashes into an ignored folder inside the clone by the bootstrap the build foundation creates (D03 T01 §17), and used from there, never from a machine install or `PATH`. Visual Studio's MSVC toolset and the Windows SDK cannot be carried and stay host prerequisites. Other tools (Python, Git, `gh`, the agent CLIs) are user-level installs; add repo-scoped wrappers where they encode project-specific behavior or reproducible commands.
- Real data only. Demo or seed data stays behind an explicit demo mode and is labeled as such.
- Develop straight on `main` (owner, 2026-11-10, reaffirmed the same day after branches for our own work were briefly allowed): no feature branches, no worktrees and no pull requests for our own work; commit to `main` and push. The only branches are the ones outside tools make by themselves (`pins/*` proposals, Dependabot, short-lived CI proof branches). Work that needs a second copy of the tree (a measurement, a parallel stream) uses a separate clone under the scratch folder, whose only branch is its own `main`; its commits reach this repository's `main` by being replayed onto it, never by a merge of a named branch, and the clone is deleted when its job ends or reused when the job recurs. `git branch -a` and `git worktree list` therefore show `main` and the tool branches only.
- Run the relevant typecheck, lint, and tests after a change.
- Fix at the owning layer: a setting in its setting, behaviour in the code that produces it, data in the data. No output filters that hide a problem. Code changes end the report with a `Layer:` line.
- Markdown prose is never hard-wrapped: one line per paragraph and per list item. Every Markdown table row stays `<= 120` characters (owner, 2026-11-10; it was 100).
- Never use em dashes or en dashes anywhere: prose, code, comments, commit messages and generated files.
- Temporary files and full logs go to scratch, never the repository: the folder the `OFFICE_SCRATCH` environment variable names (on the owner's PC `R:\scratch`, which WSL sees as `/mnt/r/scratch`), or the session scratchpad when one is given. Code never writes a machine's path: a tool finds the repository from its own location, scratch through `OFFICE_SCRATCH` (falling back to the system temporary folder), and a program through `PATH`, `vswhere` or an environment variable; `scripts/tests/test_no_hardcoded_paths.py` fails on a drive, home or mount path in a tool. A `R:\scratch\...` path in a TODO section means that scratch folder, and the code built from it resolves it.

## Safety

- Local reversible work in the repository needs no confirmation.
- Ask the operator once before anything that sends, deletes, or changes something outside the repository: mail, production systems, cloud changes, SQL writes, dropping data, credentials.
- When a command needs sudo, give the operator the exact command to run with `! sudo ...`. Never store the sudo password.
- Never print, log, or commit a secret value.
- The repository is self-contained for credentials (owner, 2026-11-10): `python scripts/import-secrets.py` copies each credential named in `scripts/lib/secret_store.py` from the Conclave vault into `.secrets/office.env` in the clone (ignored by git, closed to every other user account), and code reads a credential only through `secret_store.get`, never from the vault, WSL or an environment variable of the machine. A new credential is added to `SECRETS` there with its vault item and its shape; `python scripts/import-secrets.py --check` says which are present, by name only.
- Green dependency pull requests merge by themselves (owner decision 2026-10-21): `scripts/merge_prs.py` merges Dependabot and pins pull requests that are labelled `dependencies` or `pins`, have every check green and leave the C++ toolchain pin files (`vcpkg.json`, `vcpkg-configuration.json`, `CMakePresets.json`) alone, one at a time by rebase, at a campaign section boundary or through the `office-pr-merge` task, and never into a dirty, unpushed or mid-section clone. Local pin proposal branches (`pins/*`) still wait for the owner's merge.

## Subagents

- The lead is one long session on the latest Opus (owner, 2026-11-10, after the three-way measurement recorded in `docs/reviews/operating-mode-2026-11-10.md`: Opus building alone cost less than half of Fable alone, and Fable coordinating workers cost the most). The lead decides, plans, writes each work packet, reads every change, runs the gates and the review loop, triages findings and commits. It does not build in its own context: every section's build, and every fix round, goes to a writer that starts from a small fresh context, so the lead's context holds decisions and diffs and not the exploration that produced them. Work goes to:
  1. A script, for anything with one right answer (validate, sync, stamp, scaffolding, path checks, generated blocks). Mechanical work done twice by a model becomes a script.
  2. The Sonnet readers below, for finding facts, running suites and proving tests can fail. A Sonnet agent never writes.
  3. `section-writer` (Opus): builds one section, or one round of review fixes, from a work packet.
  4. `principal-implementer` (Fable), on call, in two cases only. First, the takeover: after review round 8 with a `P1` or `P2` finding still open, or at any round when a finding the writer reported fixed comes back, it gets the section, the whole candidate and every round's findings, and re-thinks the unit that keeps failing instead of patching the latest finding; it then writes the fix rounds for the rest of that section's loop. Second, sections whose deliverable is an architecture decision record under `docs/specs/` (Phase 3), where a wrong call is expensive to reverse, are built by it from the start.
  5. The lead itself: plan corrections, the triage of review findings, anything outward or irreversible, and any packet a worker reported `BLOCKED:` for want of a decision.
  - Haiku is retired (owner, 2026-11-10): no agent pins a Haiku model. What it was allowed for is a script's job.
  - Effort ceilings (owner, 2026-11-10): a Sonnet agent never runs above `high`, an Opus or Fable agent never above `medium`, whether the effort comes from the definition's `effort:` field or from the call. Low is the preferred effort on Opus and Fable (encouraged, not forced): the lead starts from low and chooses medium where the packet gives a reason; a takeover runs at medium.
- A build packet that fails is not a Fable case: a `section-writer` that reports `BLOCKED:`, fails its proving command twice or leaves its packet's paths is never retried on the same packet as it stands. The lead corrects the packet (a decision it had not made, a path it had not named, a packet too large that it now splits) and sends it once more; after a second failure the lead does that packet itself. `principal-implementer` is called only in the two cases above.
- A work packet names the paths that may change, the done-when, the proving command (with the test that must fail first, where there is one), what is out of scope and the scratch folder. One worker writes in the tree at a time, into a clean tree (the main loop commits its own pending edits first); readers may run beside it.
- What keeps the quality: the main loop reads the whole change of every worker before committing it (`git status --porcelain --untracked-files=all`, then `git diff HEAD`, which shows staged changes too, and every new file in full), commits only the packet's paths, and on a change outside those paths sets the whole tree aside with a named `git stash push --include-untracked` and treats the packet as failed (the rule above: corrected and sent once more, then done by the lead). It never restores or deletes to reject a packet, because a changed path may be the owner's own edit, and it never drops a stash. It also runs the proving command and the gates itself, has `mutation-tester` prove a worker's new tests can fail, and commits. Workers never stage, commit, push, stamp, review or touch `todo/`. The independent review is unchanged.
- Claude subagents pin an explicit `model:`: Sonnet for the readers, and Opus or Fable (with a `model_rationale:`) for the two workers.
- An agent reads and runs unless it is a declared worker. Every Claude subagent declares an explicit `tools:` list, never `*`; Edit, Write, MultiEdit and NotebookEdit are allowed only with `write_scope: packet` in the frontmatter, and only on Opus or Fable: a Sonnet agent never writes. No agent declares `memory:`, because Claude Code then enables Write and Edit whatever the `tools:` list says.
- An agent that gets its job wrong is removed, not kept and watched (owner, 2026-11-10: quality matters more than delegation). When the main loop's own check shows an agent returned a wrong fact, a wrong result or a claim it did not verify, delete its definition from `.claude/agents/`, its entry in the fleet list below and its lines in the Delegation sections of the skills, in one commit that says what it got wrong, and do that work in the main loop from then on. An agent that only failed to run (a timeout, an empty reply) is not removed for that.
- Run `node scripts/verify-agent-tiers.mjs` after adding, changing or removing an agent definition; it enforces these rules.
- The fleet is `.claude/agents/`: `code-explorer` (locate and map code), `git-runner` (history and diffs), `test-runner` (suites and gates, full log to scratch), `mutation-tester` (prove a test can fail), `debug-evidence` (facts about a failure), `source-researcher` (primary-source facts with URLs), and the two workers `section-writer` (Opus, builds each section and each fix round) and `principal-implementer` (Fable, on call). Which step hands what to whom, and what the main loop still checks itself, is the Delegation section of `process-todo-section` and of `review-todo-section`.

## Code intelligence

- Claude Code loads two language servers through the plugins enabled in `.claude/settings.json`: `pyright-lsp` for the Python tooling (configured by `pyrightconfig.json`, on which `pyright` reports 0 errors today) and `clangd-lsp` for C++. Use the `LSP` tool for definitions, references and call hierarchies before text search, and read the diagnostics it reports after an edit.
- Each needs its server on `PATH`, installed per user and never into the repository: `uv tool install "pyright[nodejs]"` gives `pyright-langserver`, and `clangd` is, until the tool bootstrap exists (D03 T01 §17), the one in Visual Studio's LLVM component (`VC\Tools\Llvm\x64\bin` under the installation `vswhere` reports); from then on it is the bootstrapped one. A clone installs the plugins once with `claude plugin install pyright-lsp@claude-plugins-official --scope project` and the same for `clangd-lsp`.

## TODO workflow

Plan and build through the TODO system: [docs/todo-workflow.md](./docs/todo-workflow.md).

- Every clone runs `git config core.hooksPath scripts/hooks`: its pre-commit hook refuses a TODO change committed without `python scripts/todo-graph.py plan --sync`.
- Before a section is built, one completion review (`docs/completion-review-prompt.md`) checks that building it as written gives a whole feature; each gap extends the section or is filed as a new one, and `stamp` refuses a section without that record (`process-todo-section`).
- Review rounds go through `scripts/review-dispatch.py` to the one reviewer `.conclave/reviewers.toml` pins, up to 33 rounds (22 before 2026-10-23); from round 9 on, a round whose findings are all `P3` or advisory ends the loop and its findings are filed (`review-todo-section`).
- Tests: `python scripts/run-tests.py`, or one file with `python -m unittest discover -s scripts/tests -p "test_<name>.py"` (agent tooling, TODO graph, run guard, automations and project scripts).
